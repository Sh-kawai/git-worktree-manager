# Feature Development

この skill は、ユーザーから `$feature-development` が明示的に指定された場合のみ使用する。

通常の機能追加、修正、バグ修正では自動的に使用しない。

## Workflow

### 1. MVP 要件整理

`$grilling` を使用して、今回実装する MVP の要件を整理する。

- 実装判断に必要な事項だけを確認する
- 質問しすぎない
- 将来拡張や MVP 外の仕様を掘り下げすぎない
- 既存コードから合理的に判断できる事項は質問しない
- ユーザーの判断が必要な事項を優先して確認する

要件が実装可能な粒度になったら、実装へ進む。

### 2. TDD 実装

確定した要件に従い、`$tdd` を使用して実装する。

- MVP の範囲を超えない
- 既存設計を優先する
- 不要な抽象化やリファクタリングを避ける
- 必要なテストを追加してから実装する

### 3. 差分レビュー

実装完了後、`$recipe-pr-review` を使用してレビューする。

レビュー対象は、現在の作業ブランチと派生元ブランチとの差分とする。

`gh` コマンドは使用しない。

必要に応じて以下を使用して差分を確認する。

- `git status`
- `git diff`
- `git diff <base>...HEAD`
- `git log`

レビューでは以下を確認する。

- 要件を満たしているか
- バグや回帰がないか
- 不要な変更がないか
- 既存設計と矛盾していないか
- テスト不足がないか
- セキュリティ上の問題がないか

### 4. Must 指摘の修正

レビュー結果のうち、以下を両方満たすものは `$tdd` を使用して修正する。

- `must` の指摘である
- ユーザーによる仕様判断が不要である

以下の場合は自動修正しない。

- 要件変更を伴う
- UX や仕様に複数の妥当な選択肢がある
- MVP の範囲を超える
- ユーザーの判断が必要である

修正後、必要なテストを再実行する。

### 5. 最終報告

最終回答は以下の3項目で構成する。

#### 実装内容

今回実装した内容をまとめる。
レビュー後に追加で修正した内容も含める。

#### レビュー結果

基本的には `$recipe-pr-review` の結果をそのまま出力する。

ただし以下を区別する。

- 修正済み
- 未修正
- ユーザー判断が必要
- 残っているリスクや制約

#### 動作確認項目

ユーザーが Streamlit または MUI から確認すべき項目を列挙する。

内部実装ではなく、画面上で確認可能な挙動を書く。

例：

- ○○を入力すると△△が表示される
- ○○が未入力の場合に△△となる
- ○○ボタンを押すと△△へ遷移する
- 既存の○○機能が壊れていない


入力例は具体的に提示する。
