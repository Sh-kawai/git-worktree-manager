# 個人用 Git 運用ガイド

この親管理リポジトリから扱う作業用worktreeに適用する。製品の仕様や実装方針は各worktreeの規則に従う。

## ブランチの選択

- 採用が確定した機能は対象の `feat/*` で実装する。採否を検証する機能は、そのfeatから `exp/<親機能名>/<検証内容>` を作成する。
- 例：`feat/tehai-generator` → `exp/tehai-generator/prompt-v2`。この運用では `codex/` より上記の命名を優先する。既存ブランチの改名は行わない。
- 開始時に、分岐元・戻し先のfeat、検証テーマ、採用条件をユーザーとの会話で明確にする。ブランチ名だけからGit上の親子関係を推定しない。
- 原則1ブランチ1検証テーマとし、他の未採用検証へ依存させない。不採用・未判定の変更はfeatへ取り込まない。
- 検証用worktreeの作成は [worktree管理ガイド](worktree-management.md) に従う。作成元は必ず親featを明示する。スクリプトの既定値developは使用しない。

## 自動実行の範囲

承認された実装・検証の範囲で、次のローカル操作は都度の追加確認なしに実行してよい。

- 対象の検証用ブランチ・worktreeの作成、作業ブランチ間の切り替え。
- 当該作業のファイルだけを明示したステージング。コミットとrebaseは次節の事前承認を必要とする。
- 事前に合意した採用条件を満たした検証結果の、親featへのfast-forward統合。

採用条件が未定義、結果の判断が曖昧、履歴の共有状況が不明、またはコンフリクトの解消に仕様判断が必要な場合は確認する。未コミット変更の自動退避や破棄で処理を進めない。

push、PR作成、develop・mainへの統合、ブランチ・worktreeの削除、force push、共有履歴の書き換え、変更の破棄は、対象と影響が明確なユーザーの明示的な依頼がある場合に限る。expからdevelop・mainへの直接統合は行わず、採用済み変更を親feat経由で扱う。

## コミット・rebaseの承認

コミットとrebaseは、自動実行の対象から除外する。実装や採用条件への合意、Gitコマンドの実行権限だけでは、これらの操作の承認とみなさない。

- コミット前に、対象リポジトリ・ブランチ、対象ファイル一覧（追加・変更・削除）、コミットメッセージ案を提示し、明示的な承認を求める。複数コミットに分ける場合は、各コミットのファイル一覧とメッセージ案を提示する。
- rebase前に、対象リポジトリ、書き換えるブランチ、載せ直し先、対象コミットの一覧と各コミットのメッセージ、対象ファイル一覧を提示し、明示的な承認を求める。メッセージを変更する場合は変更案も提示する。
- 承認を得た内容だけを実行する。対象ファイル、コミットメッセージ、対象コミット、または載せ直し先が変わる場合は、変更後の内容を提示して再承認を得る。
- rebaseで書き換えてよいのは、他者が利用していない検証用ブランチの履歴に限る。

## 実行前確認

1. 対象worktreeのリポジトリ、現在のブランチ、未コミット変更、進行中のmerge・rebaseを確認する。
2. ユーザーや他作業の変更を保持し、対象と重なる場合は確認する。進行中の別操作があれば独断で継続・中断しない。
3. 統合・rebaseでは、操作するブランチと親featの対応、履歴、共有状況を確認する。main・developの参照用worktreeを更新しない。
4. ステージング前に差分を確認し、当該作業の変更だけを含める。秘密情報や検証出力を混入させない。

## 採用時の統合手順

1. 検証結果を採用条件と照合し、「コミット・rebaseの承認」に従ってコミットの承認を得てから、対象変更をコミットする。
2. 「コミット・rebaseの承認」に従ってrebaseの承認を得てから、検証用ブランチ側で `git rebase <親feat>` を実行する。親featの履歴はrebaseしない。
3. rebase後の変更について必要なローカル検証を行う。有料APIや外部更新を伴う検証は既存の承認規則に従う。
4. 親featのworktreeで対象と未コミット変更を確認し、`git merge --ff-only <検証用ブランチ>` を実行する。
5. fast-forwardできなければ統合を止め、親featの更新を確認して手順2からやり直す。通常のmergeや強制更新へ切り替えない。
6. 統合先とコミット、検証結果、未確認事項を報告する。検証用ブランチ・worktreeの削除は別途明示依頼がある場合だけ行う。

## Codexの実行権限

この文書はGit操作を委任する範囲を定める。実行環境の権限を変更するものではない。権限不足時は正式な承認手続きを使う。

ユーザーが作成する `.codex/rules/*.rules` の操作別許可に合わせ、直接のGit操作は対象worktreeを作業ディレクトリにして `git <操作>` の形式で実行する。既存のworktree管理スクリプト内部の呼び出しは、そのスクリプトの手順に従う。

コマンド許可は現在のブランチや採用条件を検査しない。上記の確認を毎回実施する。既存の広い `git -C` 許可を維持すると操作別許可への限定にはならないため、許可設定の見直し時に扱う。
